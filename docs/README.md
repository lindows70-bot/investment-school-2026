# 📁 설계 문서 인덱스

기능별 설계·결정 기록. **CLAUDE.md는 "무엇을 왜 그렇게 만들었나(완료된 사실)"**, 여기는 **"만드는 도중의 계획·미결·근거"**를 담는다. 둘의 역할이 달라 중복이 아니다.

## 3종 산출물 규약

| 파일 | 무엇 | 언제 |
|---|---|---|
| `plan.md` | 무엇을 왜 만드나 + 데이터 원천 + 계산 규칙 + 정직 캐비엇 | 착수 전 (필수) |
| `checklist.md` | 체크박스 작업 목록 (Phase 0 실측 → 구현 → 검증 → 배포) | 착수 전 (다단계면 필수) |
| `context-notes.md` | 작업 중 내린 결정과 **그 이유** — 특히 **기각한 안과 근거** | 진행 중 계속 append |

실제 문서들은 9~30줄이다. **무거워서 안 지켜진 게 아니라 착수 시점에 만들 계기가 없어서 빠졌다** → `.claude/skills/feature-kickoff` 스킬이 착수 때 세 개를 함께 만든다.

⚠️ **작은 작업엔 만들지 않는다.** 버그 수정 1건·문구 교체·이미 설계된 기능의 후속 패치는 CLAUDE.md 기록만으로 충분하다. 기준: **Phase 0 데이터 실측이 필요하거나, 화면·라우트를 새로 만들거나, 세션을 넘길 가능성이 있으면** 만든다.

## 왜 `context-notes.md`가 가장 중요한가

다음 세션(사람이든 에이전트든)이 가장 비싸게 다시 알아내는 것은 코드가 아니라 **"왜 그 안을 버렸나"**다. 이 프로젝트에서 실제로 값이 컸던 기록:
- 제미나이·유튜브 제안 중 **기각한 것과 근거**(가짜 정밀·하드코딩·자동매매·중복 구현)
- 외부 API **실측 판정표**(어떤 엔드포인트가 환각이었나, 어떤 필드가 실제 키였나)
- 임계값을 그 숫자로 정한 이유

기각 근거가 없으면 다음 세션이 같은 안을 다시 제안하고, 같은 실측을 다시 한다.
